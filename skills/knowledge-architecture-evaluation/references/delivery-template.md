# 两种知识任务，分别验收

以下是合成任务和候选交付，未调用模型、用户或生产服务；不报告胜率。

## 企业支持资料

输入：`projectContext` 为 internal、validation、support-kb；工程师查型号/故障并引用资料。`corpus` 为 72,442 段，含持续修订与部门权限；token 分布未知。`currentSystem` 为已有关键词与向量检索，具体安装版本待读取。`evaluationEvidence` 有历史检索日志，没有独立答案评审。

- `projectContext`：本次结果是正确定位现行资料，保护部门权限，观察查找耗时；收入模型不作为内部验证前置。
- `comparisons`：混合检索作基线；多跳故障题试分解检索；跨产品关系题才试图谱；全库 Wiki 暂保候选，先检验混合权限和撤回代价；局部稳定手册可试 CAG，先测 token 与显存，不能凭段数断言。
- `evidenceLedger`：历史日志只能证明过去检索；模型/索引版本、来源更新率、实际延迟和答案支撑均待查。官方文档与论文结论只做候选依据，不给本项目填分数。
- `decision`：先跑受权限约束的检索基线和问题分解对照。若综合题持续缺关键事实且维护预算足够，再试编纂或图谱。决定引用当前设计的知识查询需求。
- `lifecyclePlan`：原文 v4 被 v5 替换时，关联 chunk、Wiki/graph 和缓存都失效或重算；撤回原文 A 后，共有摘要不能只删除 A 的引用仍保留其事实；ACL 切换后相同问题不可沿用旧身份缓存。
- `validationPlan`：冻结型号精确、同义问法、综合、无答案、矛盾、撤回、跨部门题；基线与候选用相同快照/身份/预算。检索 ID 指标与逐断言引用支持分开，记录冷暖缓存延迟、费用、更新成本、人工救援。
- `projectCapabilityRequirements`：projectId=support-kb；baseComponentId=applied-ai-engineer；baseComponentVersion=0.2.0；role=本项目支持知识工程师；domainEvidenceRefs=[型号表,部门权限说明]；responsibilities=[检索,派生更新,答案评审]；boundaries=[不改部门授权,不自批发布]；projectDelta=[精确型号匹配,ACL与撤回测试,项目题集]；reuseConditions=[同项目现行数据与策略版本]；targetPath=agents/support-knowledge/；requiredInputs=[资料清单,权限快照,锁文件,留出题]；toolRequirements=[仓库读取,获准离线运行]；acceptance=[越权/过期事实零容忍,其他质量门槛按本项目冻结]。宿主另建实际文件并评审，需求不冒充已创建。
- `facts`：72,442 段来自本合成案例输入；没有 token 总数、实测胜率或真实用户反馈。
- `handoff`：在现有设计中保留这些选择与缺口；宿主生成/迭代项目独立能力后绑定资料并执行。模型调用预算未有时先离线回放已有证据。

## 个人长期研究

输入改为个人持续收集论文、复用观点，单一身份、稳定小集合。推荐候选可以改为 Wiki+原始材料+搜索；用有冲突的新论文、旧论点撤回和跨文献综述检验编纂价值，仍保留简易检索对照。查询次数多也不自动证明 Wiki 更便宜，要计编纂、浏览轮次与维护。项目专业能力需知识来源、观点冲突和写作引用规则，不继承企业案例的型号表或部门矩阵。

## 拒收反例

“删除 A 后摘要还引用 B，所以摘要有效”忽略 A 的派生事实；“检索命中 90%，答案正确 90%”偷换对象；“Wiki 的旧论文分数高，所以所有知识库换 Wiki”忽略修订、任务与成本；“把 RAG、图、Wiki、CAG 全加上”没有证明各机制带来净收益。均需回到具体决定、来源或数据生命周期修复。
