# API 契约审查工作方法

## 目标与执行

检查接口是否能被真实调用、正确失败并兼容现有消费者。

1. 读取当前接口和消费者，按用户动作定位实际调用链。
2. 校验字段、可空性、枚举、状态码、分页和安全方案，再检查语义缺口。
3. 比较旧新版本，标出请求新增必填、响应移除或权限语义变化。
4. 对幂等、未知结果和异步接口写具体请求响应序列。
5. 交修正清单与最小契约用例，独立消费者可据此并行。

## 关键判断

- 当请求新增必填：按兼容变更处理并安排迁移；避免称只是加字段。
- 当写入超时：先按操作ID查询；避免直接创建新操作。
- 当规范解析通过：继续检查真实行为；避免宣布业务正确。

## 领域细节

请求和响应兼容性方向不同：请求新增必填通常破坏旧调用；响应新增字段是否兼容取决于消费者解析策略。错误对象需稳定机器码与可理解说明，重试条件不能只按所有5xx。分页说明排序稳定性、游标与数据变化。规范版本按项目选择，不强行升级最新。

## 输入不全时

- `contract`：当前和候选OpenAPI/接口说明及版本。缺规范可从真实调用归纳草案。
- `consumers`：消费者、调用流程和兼容承诺。先识别已知消费者，未知项单列。
- `examples`：真实或合成请求响应、异常和权限场景。可先写可执行契约样例，标明合成。

缺少非关键资料时，先给明确假设下的草案或局部结果；资料补齐后只重验受影响部分。授权已覆盖的可逆工作继续，不重复确认。

## 参考方法的用途

- OpenAPI Specification 3.1.1：精确定义请求、响应、错误和安全方案的接口边界。
- Stripe idempotent requests：同一业务操作重试复用身份，记录请求参数与回执。

出处和适用边界见 [PROVENANCE.md](../PROVENANCE.md)。本包方法、案例和工作单为原创整理。
