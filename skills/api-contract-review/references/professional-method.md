# API 契约审查工作方法

## 目标与执行顺序

审查接口能否被真实消费者安全调用、确定性失败并在演进中保持向后兼容，避免把“OpenAPI 语法校验通过”误判为“线上调用不断裂”。

1. **调用链映射**：读取当前契约（OpenAPI / Protobuf / GraphQL / 手写文档）与已知消费者清单，按真实业务动作串联“鉴权 → 预检 → 写入 → 查询/回调”完整路径。
2. **结构与类型审计**：逐字段检查必填性（`required`）、可空性（`nullable` / `type: ["string", "null"]`）、枚举闭合性、数值精度（金额禁用二进制浮点，统一整数最小货币单位或十进制字符串）、时间格式（ISO 8601 带时区或明确 UTC 秒/毫秒）。
3. **演进兼容性比对**：对比基线版本与候选版本，按请求逆变（Contravariance）、响应协变（Covariance）规则逐项判定破坏性变更。
4. **重试、幂等与部分失败验证**：针对超时、网络抖动、并发重复提交与异步长任务，写出完整请求—响应—查询序列。
5. **输出可执行修改单与最小契约测试**：区分阻断上线项（Blocker）、需协调迁移项（Migration）与文档补全项（Clarification），附消费者可并行执行的契约断言样例。

## 演进兼容性判定矩阵

请求与响应的兼容方向相反，审查时必须分开判定：

| 变更动作 | 发生在请求体 / 查询参数 | 发生在响应体 | 判定结论与处置方式 |
|---|---|---|---|
| 新增必填字段（无默认值） | 旧客户端缺字段直接 400 | 旧客户端若宽松解析则可忽略 | 请求侧属**破坏性变更**；必须改为可选并提供服务端默认推导，或升主版本并行双路由 |
| 新增可选字段 | 兼容（旧客户端不传仍成立） | 兼容（前提：消费者开启 `ignoreUnknown`） | 非破坏性变更；需核实移动端强类型反序列化是否拒绝未知键 |
| 删除已有字段或重命名 | 旧客户端传参被拒或静默丢弃 | 旧客户端读取空值触发空指针 | **破坏性变更**；走“新增新字段 → 双写双返 → 观测旧字段零读取 → 下线”四步弃用窗口 |
| 扩大枚举集合（新增枚举值） | 兼容（请求允许更多合法输入） | 旧客户端 `switch/enum` 可能抛异常 | **响应侧高危**；客户端枚举需定义 `UNKNOWN_DEFAULT` 兜底分支，否则按破坏性变更管控 |
| 收窄枚举集合或收紧正则/长度 | 旧客户端原合法输入变为 422 | 兼容（返回值仍是原集合子集） | **请求侧破坏性变更**；先统计存量历史数据与线上入参分布再决定是否收紧 |
| 修改 HTTP 状态码或错误码语义 | — | 客户端分支判断与自动重试逻辑失效 | **破坏性变更**；状态码与机器可读 `error.code` 一旦发布即视为契约一部分 |

## 幂等、错误模型与分页核查清单

### 1. 写操作幂等状态机（Idempotency-Key）
凡涉及扣款、下单、发券、状态流转或外部通知的 `POST` / `PATCH` 接口，不能假设网络只投递一次：
- **首次请求**：记录 `(tenant_id, endpoint, idempotency_key, request_hash)`，状态置 `in_progress`。
- **并发飞行中重试**：同一 Key 尚未完成时返回 `409 Conflict`（附 `Retry-After`）或等待原结果，严禁并发执行第二次副作用。
- **完成后重放**：同一 Key 且 `request_hash` 一致时，直接原样返回首次持久化的状态码与响应快照。
- **参数篡改重放**：同一 Key 但 `request_hash` 不同时，明确返回 `422 Unprocessable Entity`（`IDEMPOTENCY_KEY_PAYLOAD_MISMATCH`），拒绝静默采用新参数。

### 2. 结构化错误契约（参考 RFC 9457 Problem Details）
禁止用 `200 OK` 包裹 `{"success": false, "msg": "系统繁忙"}` 或只返回自然语言字符串：
- 必须区分**调用方修正入参可解**（`400/404/409/422`，禁止原样盲目重试）、**凭证刷新可解**（`401` 刷新令牌、`403` 权限不足不重试）、**限流退避可解**（`429` 配合 `Retry-After`）与**服务端瞬态故障**（`502/503/504`，仅对带幂等键或只读接口做指数退避 + Jitter 重试）。
- 错误体至少包含：稳定机器码 `code`、人类可读说明 `message`、请求追踪号 `requestId`、字段级定位 `fieldErrors[]`（含字段路径与违反原因）。

### 3. 分页、排序与并发写入一致性
- 动态增长列表优先使用基于稳定唯一排序键的游标分页（`(sort_ts, id) < (cursor_ts, cursor_id)`），避免深翻页 `OFFSET` 性能退化及新插入数据导致的漏读/重读。
- 明确声明 `nextCursor` 为不透明令牌（Opaque Token），消费者不得自行拼接或解析内部表主键；到底页时明确 `hasMore: false` 且 `nextCursor: null`。

### 4. 鉴权与租户越权边界（BOLA / IDOR）
- 检查路径或请求体中的资源 ID（如 `/orders/{orderId}`）是否声明归属主体校验规则，防止仅凭登录态即可横向遍历其他租户或用户的资源。
- 区分用户态 Token、服务间 M2M 凭证与 Webhook 签名验签（含时间戳防重放窗口与常量时间签名比对）。

## 输入不全时的降级与推进规则

- **`contract` 缺失或不完整**：可从真实路由代码、DTO 定义或抓包样例反向整理契约草案，明确标注“从代码/样例归纳，待确认为正式契约”。
- **`consumers` 未知**：先按最严格的外部公开客户端标准（强类型解析、旧版长期存活、移动端发版周期长）标注风险，单独列出需向调用方核实的未知项。
- **`examples` 缺失**：自行构造覆盖正常路径、边界空值、幂等重放与权限拒绝的最小请求—响应样例，并显式标明为合成契约样例（Synthetic Contract Fixture）。

缺少非阻塞资料时，先交付明确假设下的审查矩阵与最小契约用例；资料补齐后仅增量重验受影响接口。

## 参考规范与来源边界

- **OpenAPI Specification 3.1.1**：统一 JSON Schema 2020-12 可空性与多态结构定义，精确约束请求、响应、安全方案与头信息。
- **Stripe Idempotent Requests**：同一业务写操作通过幂等身份隔离网络重试副作用，校验请求参数摘要并持久化回执。

出处与适用边界见 [PROVENANCE.md](../PROVENANCE.md)。本包审查矩阵、用例模板与判断规则为原创整理。
