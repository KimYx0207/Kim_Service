# 需求与验收证据追踪

把每个交付义务与来源、实现位置和实际验收记录连接，及时暴露遗漏、过期证据与局部阻断。

## 开始前

- `requirements`：当前需求/验收条件、唯一ID、版本和来源 缺失时：先给缺口，不为模糊要求伪造已通过
- `artifacts`：设计、代码、文档、执行/测试记录与版本 缺失时：未给证据只映射计划，状态未观察
- `changes`：变更、依赖、接受责任和已获决定 缺失时：缺决定保留待定，独立范围可继续分析

## 执行

1. 阅读 [工作方法](references/professional-method.md)，先确定适用条件与证据范围。
2. 沿 [专业方法](method.json) 的 `steps` 执行具体操作，再用 [完整交付模板](references/delivery-template.md) 整理当前产物；诊断问题与空字段不能充当完成。
3. 按 [专业质量规则](method.json) 中的具体输出规则选择检查方法，保存本次输入/产物定位及未观察项。
4. 对照 [作者正反例](evals/professional-cases.json) 检查常见专业错误；作者预期不算本次评测结果。
5. 把规则结果、实际产物、未决问题交回调用方；缺口仅影响相关结论。

## 交付

- `traceMatrix`：需求到实现和验证的双向矩阵。
- `evidenceAssessment`：逐项证据适用判定。
- `impactMap`：变更影响与失效记录。
- `acceptancePacket`：接受材料与未决事项。
- `facts`：当前输入、来源、期间单位及证据缺口。
- `limitations`：未执行、未观察、方法假设和外推边界。
- `handoff`：当前产物、规则结果、证据定位与待解决事项交调用方。

## 关键验收条件

- `traceMatrix`：每个当前必需要求有来源、责任、实现/产物、验证方法和证据状态；反向标无对应要求产物。 拒收：缺需求行、用一个笼统完成覆盖所有要求或把额外产物自动当必要。
- `evidenceAssessment`：核原始运行、需求/输入/规则/实现版本、工作区差异、环境、范围和实际结果；分支名、哈希与发生性分开判断。 拒收：文件存在、hash一致或同为main便算当前通过，旧输入/规则/共享依赖变化被忽略。
- `impactMap`：在保留旧基线后比较当前变化，沿要求/接口/配置/共用实现/证据定位需重验、可保留与关系未知的范围，说明每条理由。 拒收：覆盖旧基线后自比、叶文件没改就继承旧通过、把未知依赖当无影响，或无依据全量失效。
- `acceptancePacket`：关键失败/未知独立列出，明确决策者和受影响范围；结果交调用方。 拒收：总通过率掩盖关键失败或把自检标为最终接受。

全部检查方法、证据要求和阻断标记以 [method.json](method.json) 为准。规则未执行时记录未观察；教学案例不是已经完成的专业评测。

## 边界

追踪表不替代实际测试或人工接受；本包不决定跨模块调度和最终批准。

最终接受、关键要求豁免及不可逆范围变更交有授权的业务/工程责任人决定。

只读本次指定材料；实际联网、命令、发布、业务变更或外部消息依当前宿主授权。方法不接管跨组件调度、持久记忆或最终验收。合同和示例检查不证明真实宿主或行业效果；无执行证据保留 needs_probe / not_evaluated。
