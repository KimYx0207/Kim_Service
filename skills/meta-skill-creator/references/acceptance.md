# Skill 改进应由什么证明

## 按产物选择工具

照片、插画、表情等栅格创意画面优先使用可用的宿主生图；精确统计图用数据与绘图库，保留数据与可复算过程；可编辑表格用表格文件和公式；文档保留文档结构；原生界面用代码与可操作预览。后几类不是生图失败后的降级。已有Multimodal Route规则只在确定需要栅格创意图后应用，工具缺失也不能偷偷改变交付类型。

## 从失败变成方法

先定位失败发生在哪层：触发错误、专业判断缺失、输入不合法、工具使用错误、产物有误、报告夸大。只针对对应层增加知识/规则/脚本。给“前端专家”加两行角色描述无法解决键盘导航；应给明确语义结构、焦点、状态、回归方法及真实对照产物。

入口体积预算只是加载成本，不是专业评分。领域方法是否覆盖关键例外、是否改变实际任务决策、产物能否通过反例检查，才是质量证据。纯文字技能未必需要额外脚本；没有合理用途的文件不应为凑“非文档资产”而新增。

## 最小完整交付示例：CSV标识符审查

合成失败材料：原文件order_id是00123，旧输出变成123。需求是保留标识符并对缺必填列报错。选择修改已有导入审查包，保留解析器；新增字段类型规则，入口在遇标识符时读取，输出保留可编辑CSV和诊断报告。正例输入为order_id=00123；反例为缺order_id列、混入空值和数值转换。通过标准在运行前冻结：原字符串保留、缺列拒绝且定位、未改无关列。

完整改动报告给包决定、实际changedFiles、triggerBoundary、progressiveLoading、validationPlan、remainingGaps；每个文件对应上述失败之一。运行前只有设计和合成样本，报告候选；运行后用相同输入比较新旧实际产物，留时间、版本、输入/输出绑定。只运行JSON校验时evidenceLevel=structure，不能宣称已达到专家水平。

## 两种会被拒收的“完成”

1. 准备器生成完整acceptance目录，所有字段填齐，然后把pending改pass。缺少真实session、实际输出和独立发生性，仍未通过。文件哈希互相匹配只说明内容一致，不证明发生。
2. 100分里拿95分，但00123仍变123。关键业务条件失败，不允许平均分抵消。评分可比较已满足关键条件的方案；不能把错误答案升成可发布版本。

沿用evaluation-method.md和closed-loop-governance.md的现有机制，不新建评价状态源。本文件与professional-cases.json是作者设计的标准及示例；真实前测应由未看预期答案的独立执行者产生原始产物，再由审核者按已冻结标准评估。

## 加载与评估边界

执行本能力时按 SKILL.md 读取本文件及 method.json 中当前 capabilityId 的诊断、决策与 outputChecks。使用已有脚本和引用资料，不另造调度或运行状态。每条 blocking 规则缺证据或失败时保持未验收；其他高分不能抵消。作者自报 pass 最多是待独立复核的线索。

本仓库校验器验证合同、引用和示例格式；professionalEffect=not_evaluated。professional-cases.json 是作者合成的教学正反例，没有真实运行或人审发生性。当前 Meta 的 Skill 发现路径不会像 Agent 方法投影一样自动把 method.json 注入 worker；实际加载依赖入口的明确阅读规则和宿主支持，未观察则如实报告。原生宿主是否触发、业务效果是否改善，都必须另取当前版本的实际任务证据。
