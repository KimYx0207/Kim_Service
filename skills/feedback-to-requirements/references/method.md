# 反馈转需求证据台账 方法

## 判断顺序

1. 接收同一公司 Work/项目内的原始反馈及来源，保留客户 ID 或匿名状态。
2. 检查重复引用存在性和环路，只采用调用方明确的分组。
3. 生成带证据哈希的需求候选、客户去重计数、未分类和矛盾清单。
4. 只有匹配候选版本与材料的既有采纳回执生效；新候选保持 proposed。

## 关键界限

重复反馈显式引用原条目；状态、引用和操作者边界分开核查。

候选哈希绑定公司、Work 及其修订、项目、采纳角色与完整候选。`sourceRecordIds` 是调用方选入的反馈，`evidenceRecordIds` 另列参与证据核验的完整重复引用链，以及直接相关矛盾的全部反馈和重复引用链；`evidenceSha256` 对这些原始记录及相关矛盾一起计算。引用链中的组外条目或相关矛盾发生变化，旧采纳会失效；不相关的反馈变化不会让已核对候选重复审批。

不复制 AGPL 源码，不接管产品库，不自动判定语义重复，不用点赞数冒充独立客户数。

## 失败后恢复

同一客户多次反馈算成多个人，或跨项目合并后隐藏来源。 修正相关来源/版本后重跑本地 helper。每个输出包含完整输入与政策哈希；对超限材料明确分包，保留原文件，不静默裁剪。采用记录由调用方提供并绑定本次对象版本；脚本不能证明操作者真实身份。

## 与已有能力配合

原文分析交给 source-evidence-analyst；检索排名交给 retrieval-evaluation；产物字节与 Work 交接交给 delivery-verifier。保留各自职责，不能用本包的结构检查替代领域判断、最终采纳或真实运行回执。
