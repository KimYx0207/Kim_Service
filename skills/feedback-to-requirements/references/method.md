# 反馈转需求证据台账：方法与去重口径

## 核心问题：为什么原始反馈汇总经常误导产品排期

产品团队整理用户反馈时最常见的四类失真：
1. **声量错觉（Vocal Minority）**：1 家客户在群里、工单、销售周报里重复反馈 8 次，被不同渠道重复录入后误判为“高频共性需求”。
2. **匿名与互动指标混同**：把社区帖子点赞数、转发数或未登录匿名留言直接加总进“独立受影响客户数”。
3. **过度聚类抹平关键分歧**：把“希望默认折叠高级参数”和“希望一打开就平铺全部参数”都归入“优化配置页体验”，导致上线后激怒另一半重度用户。
4. **僵尸审批继承**：需求背后的客户证据或反面冲突已经发生重大变化，台账仍沿用三个月前的“已批准”状态。

## 计数、引用链与哈希绑定规则

| 台账要素 | 严格计算口径 | 错误做法（必须拦截） |
|---|---|---|
| **总反馈条数 vs 独立客户数** | `rawFeedbackCount` 统计关联的去重条目总数；`distinctCustomerCount` 仅对非空、已识别的唯一 `customerId` 去重计数；匿名条目单独计入 `anonymousRecordCount` | 将同一 `customerId` 多条工单算作多个客户，或给每条匿名记录随机编造不同 `customerId` |
| **显式重复引用链（`duplicateOf`）** | 校验引用目标存在且无环路（A→B→A 立即报错阻断）；沿传递闭包收集整条重复链上的所有原始条目进入 `evidenceRecordIds` | 忽略组外被间接引用的原始记录，导致根反馈修改时漏触发重审 |
| **正反矛盾证据保留** | 当客户诉求与候选方案方向相反（如简化 vs 保留细粒度控制），显式挂接在矛盾清单中并纳入同一候选的证据边界 | 为让需求提案显得一致而静默剔除反对意见 |
| **证据与采纳哈希失效机制** | `evidenceSha256` 同时覆盖候选关联的 `sourceRecordIds`、完整重复引用链及关联矛盾记录；只有版本、组织、Work 修订、角色与哈希全部吻合的采纳回执才生效 | 底层支撑证据已增删或矛盾加剧，仍保留旧版 `accepted` 状态；或因不相关的其他需求新增反馈而误清空本需求的已核对状态 |

## 四步执行与核查流程

1. **范围与来源核验**：确认全部反馈记录归属同一组织与目标项目，保留原始渠道标识与提交时间，不跨项目混算客户基数。
2. **图结构完整性检查**：检查每条 `duplicateOf` 指向有效记录且构成无环森林（DAG），检查需求分组未引用不存在的条目 ID；未归入任何候选的反馈自动进入 `uncategorized` 兜底池，确保**零反馈静默丢失**。
3. **生成可审计需求候选**：按候选逐项输出独立客户数、匿名条数、完整证据 ID 集合、矛盾证据摘要及 `evidenceSha256`。
4. **状态对齐与人工交接**：比对调用方传入的既有采纳回执，输出生效状态与失效原因，交产品负责人结合商业价值与研发成本做最终排期。

## 失败后恢复与协同分工

- 遇到环路引用、悬空 ID 或跨项目混入记录时，根据明确报错定位修正输入 JSON 后重跑 `node scripts/run.mjs --input-json -`；每次输出均附带 `inputSha256` 与 `policySha256`。
- 超出单次容量上限的大批量历史工单，按时间窗口或产品模块分包运行并保留原文件引用，禁止静默截断尾部反馈。
- **职责协同**：长篇访谈录音/文档的原文切片提取交给 `source-evidence-analyst`；需求落入研发后的字段级正向/反向追踪交给 `requirements-traceability`；架构切片与排期路线交给 `product-architect`。来源与许可证说明见 [PROVENANCE.md](../PROVENANCE.md)。
