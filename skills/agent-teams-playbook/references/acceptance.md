# 团队交付验收

## 执行前后各看什么

先给节点写产物边，而不是只写先后序号。A 产生接口字段表，D 消费它，才需要 A→D；B 文案和 C 可访问性检查不消费 A 的结论，就不应等待 A。资源冲突是另一条约束：两个“无依赖”工单若都改同一文件，也不能无隔离同时写。

人工门记录问题、待审产物版本、允许继续的后继和恢复条件。用户批准 fields-v2，不能用于 fields-v3。运行状态由当前宿主/Meta 的既有状态源维护；本 Skill 的表格只是可读投影。LangGraph 中断可能从节点开头重放，调用方需把不可重复副作用放在可验证的宿主边界；不能靠一句“已处理”避免重复付款。

## 最小完整交付示例

合成任务：A 审字段、B 改文案、C 做可访问性清单、D 用批准字段实现表单。容量 2；B 写 copy.md，C 写 checklist.md。当前 A 等待 fields-v2 审核；可运行集合为 B、C，D 等待 A。此刻报告“已准备 B/C 工单，尚无启动回执”，不能写“两名 Agent 正在跑”。

最终合格报告需包含：A 对 fields-v2 的具体决定；B 的 copy-v1；C 的 checklist-v1；D 消费 fields-v2 的实现版本；独立检查者观察到键盘能提交有效输入、错误输入保留用户填写内容；剩余未覆盖浏览器清楚列出。每份产物有本轮路径或返回文本及版本，合并者核对实际版本。这段是报告形状示例，不是这些行为已经在仓库执行。

## 拒收与恢复

- A 等待而 B/C 被一起停止：重新计算真实依赖，继续独立支线。
- D 引用 fields-v1 或把 A 的“建议批准”当批准：只重开 D 和受影响验收，不重跑 B/C。
- 接口测试通过但提交按钮无法键盘触达：整体验收仍未通过，不能用测试数量抵消。
- 某任务失败：判断输入问题、工具不可用、暂时故障或设计冲突；只有改变了失败条件且预算允许才重试。没有进展就报告可恢复检查点，不机械凑两轮。

已有宿主 profile、安装脚本及阶段流程仍是执行入口。Zcode、DSh 或新宿主按实际工具映射；未观察到 spawn 时只执行顺序路线。

## 加载与评估边界

执行本能力时按 SKILL.md 读取本文件及 method.json 中当前 capabilityId 的诊断、决策与 outputChecks。使用已有脚本和引用资料，不另造调度或运行状态。每条 blocking 规则缺证据或失败时保持未验收；其他高分不能抵消。作者自报 pass 最多是待独立复核的线索。

本仓库校验器验证合同、引用和示例格式；professionalEffect=not_evaluated。professional-cases.json 是作者合成的教学正反例，没有真实运行或人审发生性。当前 Meta 的 Skill 发现路径不会像 Agent 方法投影一样自动把 method.json 注入 worker；实际加载依赖入口的明确阅读规则和宿主支持，未观察则如实报告。原生宿主是否触发、业务效果是否改善，都必须另取当前版本的实际任务证据。
