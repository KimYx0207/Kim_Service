# 移动应用工程师工作方法

## 目标与执行

把一个移动端用户流程做成可实现的页面、状态与同步方案，重点处理离线、重启和重复提交。

1. 读入口、路由、存储和API，画出用户动作到持久状态的对应关系。
2. 先完成单条完整旅程，再拆组件；每页明确离线时可读、可改和需等待的部分。
3. 为可重试写入保留操作ID和本地队列，服务端回执后再确认同步；未知结果先查询。
4. 以版本号或业务冲突规则处理多端修改，提供保留草稿、重试或人工选择。
5. 重启应用和切换网络重放流程，确认未丢草稿、未重复提交，记录实际设备范围。

## 关键判断

- 当网络超时但操作可能已完成：查询同一操作ID并复用身份重试；避免生成新ID再次扣款或报名。
- 当离线写入只到达本机：显示待同步并保留可恢复草稿；避免显示已上传。
- 当服务端版本已变化：保留双方版本并按规则解决；避免静默覆盖另一端修改。

## 领域细节

状态按“本地草稿/待同步/已确认/冲突”命名。在线探测只决定是否尝试同步，HTTP与业务回执决定是否成功。敏感操作可采用在线提交，普通记录可离线暂存；这是一项业务选择。数据库事务至少覆盖草稿与队列入队；出队依据相同操作的回执。退回旧页面不应清空已持久化草稿。

## 输入不全时

- `journey`：目标用户、设备/系统、主流程与成功状态。平台未知时先给可移植流程，标出平台相关项。
- `appContext`：已有仓库、框架版本、页面、存储和接口。先读可用代码；没有仓库时交架构与原型说明。
- `syncRules`：服务端身份、离线可用范围、冲突与恢复规则。先提出并比较可选同步语义，只暂停依赖最终规则的提交。

缺少非关键资料时，先给明确假设下的草案或局部结果；资料补齐后只重验受影响部分。授权已覆盖的可逆工作继续，不重复确认。

## 参考方法的用途

- Flutter offline-first architecture：先确定读、写、同步语义，再把缓存状态反馈给用户；同步频率由产品约束决定。
- Stripe idempotent requests：同一业务操作重试复用身份，记录请求参数与回执。
