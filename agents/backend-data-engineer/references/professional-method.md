# 服务与数据工程知识装配

方法版本：0.2.0。仅服务当前 backend-data-engineer 任务；来源见 ../PROVENANCE.md。这里是原创检查方法，不能代替所用数据库和框架版本文档，也不授予数据库、网络或生产权限。

## 输入与版本取证

读取指定服务入口、路由、身份校验、模型、迁移和相关测试，记录实际运行时/数据库/驱动/ORM 版本的证据；锁文件声明与数据库服务版本分别记录。没有数据库回执时只能说明代码假设。优先沿用现有事务、错误码、审计和迁移约定；新的技术选择交 product-architect 进入当前 designContext，不自行换栈。

把 dataContract 和 serviceContract 展开为主体、动作、对象、租户边界、输入白名单、返回字段、状态码、并发语义与失败恢复。对于每个写操作，回答“谁有权改哪个对象；什么必须一起成功；失败后重试是否会重复”。输入中 owner、role 或资源 ID 都不能自行证明权限。[owasp-bola]

## 核心工作方法

1. 身份必须来自实际验证链；逐对象校验主体是否有权执行当前动作，覆盖批量、嵌套对象和下载路径。不可预测 ID 也不等于授权。跨用户失败不能回传对方数据或泄漏对象是否存在。
2. 数据完整性落实到当前数据库可执行的约束与事务；只在应用里“先查再写”无法证明并发安全。选择唯一约束、条件更新或锁时说明冲突和重试语义，先核实数据库/驱动支持。
3. 幂等键要绑定主体、动作和请求语义；同键不同参数必须处理冲突，不能复用他人的结果。外部副作用不因本地事务回滚而自动撤销；有实际需求再选择持久任务或补偿方案。
4. 分页必须明确稳定排序与边界，限制请求大小、超时和返回字段；日志脱敏。保留旧客户端兼容性，字段新增、改义与删除分别说明。
5. 迁移按兼容扩展、验证和收缩列步骤；用本地受控副本验证数据不变量与恢复方法。删除旧路径前查路由、配置、作业、外部消费者与保留义务，保留证据；无生产授权只交计划。

## 正例与反例：带版本的草稿更新

事实：用户 A 可以编辑自己的草稿，B 无权限；草稿版本是 7；请求包含预期版本。测试必须使用真实目标数据库或明确标为替身。

反例：信任 body.owner；按 id 先读取再无条件更新；对所有零行更新返回含最新正文的 409。这可能越权、覆盖并发修改或泄漏 B 的正文。

正例：先建立已验证主体的对象权限，条件写入绑定对象和预期版本；冲突只在已获对象访问权后返回允许的差异信息。让两个有效写入同时使用版本 7，验证只产生一个预期版本推进，另一个按约定失败；具体事务边界和错误码从实际栈决定。禁止把这段描述当作已验证 SQL。

## 验收矩阵

| 场景 | 观察和可接受证据 |
| --- | --- |
| 同租户允许/跨用户拒绝 | 真实请求状态、返回字段和数据库变化；同时验证读与写 |
| 同版本并发写入 | 控制并发时序，核对成功数、版本值、正文及失败信息 |
| 重复/冲突幂等键 | 同请求重放不重复副作用；不同请求语义不会错领旧结果 |
| 事务中断/超时 | 失败前后关键数据不变量与重试结果 |
| 迁移和恢复 | 实际副本版本、迁移输出、旧客户端兼容证据及恢复后的数据检查 |

testEvidence 区分 mock、local_database、host_service 和未执行；记录代码版本、数据库版本、输入、预期、观察、命令/回执和 criterionId。认证函数的单测不能证明整条授权链。没有真实数据库时交实现候选及具体缺口，不称“事务已验证”。knowledgeUsage 只引用实际加载或核实的资料。
