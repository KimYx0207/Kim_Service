# 可靠性工程师交付示例与工作单

## 已完成的教学示例

以下输入为合成案例，数字和状态用于演示复核方法。

```json
{
  "service": "活动报名API",
  "signals": {
    "baseline": {
      "requests": 10000,
      "errors": 20
    },
    "canary": {
      "requests": 200,
      "errors": 6
    }
  },
  "release": "同时间同类型请求，错误率上限1%，最少100请求"
}
```

- **serviceObjectives**：基线0.2%，候选3%；候选200请求达到本次下限。
- **rollout**：3%超过1%，停止候选放量并回退报名API；导出接口不受影响。
- **recovery**：保留已完成报名回执，回退后用同操作ID查询状态；冷却后5条探测通过才恢复观察。
- **observability**：记录版本、路由、错误分类和请求ID。

## 为什么退回这一份

无请求直接推广：{"rollout": "候选0次请求0错误，所以错误率0%，全量上线。"}

错误原因：零分母没有提供质量证据。

## 可以继续的局部结果

资源指标与体验分开：{"serviceObjectives": "CPU正常但报名500错误增加，按报名失败计入SLO；CPU只作诊断线索。"}

用户结果是评价对象。

## 用于当前任务的工作单

| 交付项 | 本次应填内容 | 检查方法 |
| --- | --- | --- |
| serviceObjectives | 明确成功/合格请求、窗口、分子分母，指标能对应用户体验。 | deterministic_recompute |
| rollout | 对照同类基线按样本量和关键指标推进，失败只停止候选范围。 | behavior_probe |
| recovery | 明确识别、止损、回退、核验和恢复条件，执行者能找到对象。 | behavior_probe |
| observability | 告警包含影响、责任和操作入口，减少重复无动作信号。 | artifact_inspection |

用真实输入替换示例并保存产物位置。关键业务错误只阻断受影响的结论或操作；格式和解释完善不要求全任务停下。
