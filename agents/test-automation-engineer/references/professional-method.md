# 自动测试工程师工作方法

## 目标与执行

围绕真实用户路径建立有判定力的自动化测试，让失败可复现、可定位。

1. 从用户完成标准和本次差异选高价值路径，确定每项的可观察结果。
2. 建立独立账号/数据夹具，明确哪些第三方依赖mock、哪些真实联调。
3. 实现语义定位、自动等待和结果断言，校验保存后的刷新或重新查询。
4. 用失败服务、重复提交、权限变化和取消恢复检查产品行为。
5. 保留首跑失败trace，修复根因后再跑受影响集；把无法稳定复现的条件写清。

## 关键判断

- 当提交操作完成：刷新或重新查询持久化结果；避免只判断按钮点击成功。
- 当测试重试后通过：保留首跑失败并诊断；避免删除失败记录称稳定。
- 当异步页面：等待业务状态或可重试断言；避免用固定sleep掩盖竞态。

## 领域细节

独立测试可并行，修改同一全局状态的测试应隔离或串行。页面保存可用返回对象ID和重新读取核对，避免只看toast。视觉比较固定字体、视口、时区与动态内容，但关键交互还需操作验证。失败报告应使另一人能从入口和数据复现。

## 输入不全时

- `behavior`：用户流程、业务规则、关键失败和完成标准。先选最重要的可观察结果。
- `system`：运行入口、测试环境、账号/数据与依赖。缺运行环境可先写测试计划和可执行脚本。
- `changes`：本次差异、风险和已有测试。从受影响路径选择范围，避免机械全测。

缺少非关键资料时，先给明确假设下的草案或局部结果；资料补齐后只重验受影响部分。授权已覆盖的可逆工作继续，不重复确认。

## 参考方法的用途

- Playwright best practices：围绕用户行为、独立测试状态和可重试断言编写测试。
- Storybook accessibility testing：为组件各状态配套可检查故事和自动化可访问性检查。
