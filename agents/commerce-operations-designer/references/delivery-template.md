# 商业订单运营设计师交付示例与工作单

## 已完成的教学示例

以下输入为合成案例，数字和状态用于演示复核方法。

```json
{
  "journey": "电商订单含部分退款",
  "records": "实付10000分，退款R1=2500分成功，重复通知R1再次到达",
  "policies": "重复事件去重，退货验收后入可售"
}
```

- **stateModel**：订单已付款，部分退款成功；退款状态独立于发货。
- **eventHandling**：R1通知两次仅一项退款效果，累计退款2500分。
- **reconciliation**：净收10000−2500=7500分；退回商品仍待验，不增加可售数。
- **operationsPlaybook**：退款回执未知时查询R1状态；不生成新退款ID。

## 为什么退回这一份

重复退款：{"reconciliation": "R1到两次，退款累计5000分，净收5000分。"}

错误原因：重复通知被当作两次业务效果。

## 可以继续的局部结果

晚到旧事件：{"eventHandling": "已支付后收到旧pending事件，保存通知但不把支付状态倒退。"}

事件发生时间和状态规则共同决定更新。

## 用于当前任务的工作单

| 交付项 | 本次应填内容 | 检查方法 |
| --- | --- | --- |
| stateModel | 订单、支付、履约、退款分开建模，定义允许转换和金额上限。 | artifact_inspection |
| eventHandling | 稳定事件身份去重，未知结果查询，乱序不使状态倒退。 | behavior_probe |
| reconciliation | 已付减成功退款等于净收，实物状态与可售库存分别核对。 | deterministic_recompute |
| operationsPlaybook | 明确超时、缺货、部分退款和取消入口及责任。 | artifact_inspection |

用真实输入替换示例并保存产物位置。关键业务错误只阻断受影响的结论或操作；格式和解释完善不要求全任务停下。
