# 商业订单运营设计师工作方法

## 目标与执行

把下单、支付、履约、退换和订阅续费连接成可追踪的运营状态与异常处理。

1. 分别梳理订单、资金、履约与库存状态，标出各系统权威来源。
2. 定义事件ID、业务操作ID和转换条件，区分通知已接收与业务已完成。
3. 处理重复、乱序、部分退款和回执丢失；先查询真实状态再重试。
4. 按金额和实物状态对账，退货验收前不恢复可售库存。
5. 用一批合成异常事件回放流程，给人工队列和可恢复操作入口。

## 关键判断

- 当收到重复事件：只消费一次且可查询处理结果；避免再次触发发货。
- 当发生部分退款：累计成功退款不超过实付并保留行项目；避免按请求金额当成功金额。
- 当退货在途：记待验库存，验收后决定可售；避免直接加可售库存。

## 领域细节

事件去重范围绑定店铺/租户和供应商，避免不同店铺相同ID冲突。金额按最小币值及币种核算，优惠、税、运费和退款分开。订阅计划状态与一次付款状态不同：取消未来续费不撤销已发生服务。对账可发现孤儿付款、未发货和退款缺回执，分别进入可操作队列。

## 输入不全时

- `journey`：订单类型、渠道、支付、履约和售后流程。先建立一条订单完整状态表。
- `records`：订单/支付/库存/退款事件及版本。没有生产记录可用合成事件验证流程。
- `policies`：取消、退款、库存归还、订阅与服务时限。政策待定时列选项，不阻断独立订单流设计。

缺少非关键资料时，先给明确假设下的草案或局部结果；资料补齐后只重验受影响部分。授权已覆盖的可逆工作继续，不重复确认。

## 参考方法的用途

- Shopify webhook delivery verification：核对事件身份与重复投递，再处理订单状态变化。
- Stripe idempotent requests：同一业务操作重试复用身份，记录请求参数与回执。

出处和适用边界见 [PROVENANCE.md](../PROVENANCE.md)。本包方法、案例和工作单为原创整理。

## 可运行参考计算

本包提供 `scripts/replay-money-events.mjs`，以命名导出函数处理明确输入；运行 `node tests/calculation.test.mjs` 可复算本例和边界反例。它是局部参考算法，生产环境的权限、数据来源和完整业务路径仍按当前任务核验。
