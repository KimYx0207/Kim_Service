# 从预约需求到可迁移的系统设计

这是本包的原创合成工作样例，用于说明专业步骤、完整交付和拒收条件。它不是真实客户成果，也不是模型效果评测；实际任务替换输入与约束，按当前标准独立核验。

## 实务任务与边界

合成任务：一家三人服务团队用表格管理预约，希望客户在线预约，工作人员确认后生效。已有客户资料不能丢，当前每周约200笔预约，暂不做在线支付。交付目标是可实施的设计和迁移方案，人数与流量是本例输入，不是选型阈值。

## 先完成的专业判断

1. 将“预约成功”拆成提交、待确认、已确认、已取消。问清谁确认、同一时段容量、临近服务的取消规则、时区和通知失败的处理。未确定的规则进入待决表，不藏在技术选型里。
2. 盘点现有表格字段、客户重复记录、权限和更新入口。预约记录与客户记录各有一个权威来源；页面缓存与搜索索引是派生数据。
3. 比较可行方案：现有工具扩展适合低定制流程；模块化应用适合明确的状态与权限需求；分布式服务须有独立扩容、团队或可靠性依据。本例先比较前两种，不能把“可扩展”自动翻译成微服务。
4. 为每项选择记依据、代价、撤回成本和触发复议的变化。接口与状态责任先达成一致，再细化前端、后台与通知任务。

## 最小完整交付样例

| 设计项 | 本例可交付内容 | 对应验证 |
| --- | --- | --- |
| 领域状态 | pending → confirmed；pending/confirmed → cancelled；取消不删除审计记录 | 每条转换有执行者、前置条件、重复请求处理 |
| 预约接口 | 创建请求携带业务幂等键；响应含预约ID和当前状态 | 相同幂等键重试只形成一个预约 |
| 容量约束 | 确认时在同一事务内检查容量并保留名额 | 并发确认不能超卖；仅页面按钮禁用不够 |
| 通知 | 预约状态提交后记录待发通知，重试与去重独立 | 通知失败不能把已确认预约回滚成未提交 |
| 模块边界 | 预约规则、客户数据、通知适配、展示各有单一责任 | 展示层不直接改预约表，通知不批准预约 |
| 迁移 | 字段映射、去重规则、试导入对账、回滚窗口、旧入口切换 | 记录数和关键业务金额/容量按口径核对，不能只比行数 |

正式输出将这些内容放进现有 scope、architecture、migration 字段，并附关联需求ID和实际资料引用。技术栈只写仓库实际版本或有依据的候选，不虚构性能压测。

## 变体与拒收

- 多门店：补门店隔离、跨门店权限和各地时区，再决定是否共享容量；不能仅加一个storeId而不查访问路径。
- 引入付款：先定义支付与预约的一致性、超时、退款及对账，再新增模块；不能把付款状态直接等同履约完成。
- 导入存在同名客户：使用经确认的匹配规则与待人工复核列表，不能把名字作为唯一键。
- 只有架构图、没有状态转换和迁移核对规则，拒收；技术选择无法指向用户约束或实测依据，退回补证据。
