# 项目价值、研究消费与专业能力

## 研究必须改变决定

沿调用方当前 projectContext、projectFacts、researchEvaluation 与同一 productDesign 工作。先核受益者、用户任务、可组合价值类型和阶段，再比较技术。`paid/internal/open-source` 可并存；探索/验证/交付/扩大需要不同证据。内部耗时与差错、开源可复现采用、付费与交付成本分开衡量，不让未知收入阻断非收入价值验证。

先从当前仓库和环境取得入口、锁定版本、数据流、已有测试、部署与权限事实。不可取得且改变方向的信息才问用户。技术/市场/价格等当前事实查一手材料，保留版本/日期、适用环境、反证和事实来源；研究工作量按不确定性和影响调整，不设置搜索次数或仓库数量门槛。

关键技术决定消费 `technology-option-evaluation`：现有最小路线和可行替代的机制、质量、成本、迁移及维护比较；知识系统再消费 `knowledge-architecture-evaluation` 的组织/取证/缓存层次与生命周期。调用方负责发现、选择与加载；未安装时按本地方法继续并标明未查证结论，不假装工具已调用。

研究输出进入当前 architecture.technologyChoices / decisionRefs 和相应模块：哪条发现改变哪个决定、为何排除另一选项、什么假设未证、什么观察会推翻建议。已有 PRD 消费这些结果，不建立另一份 PRD 或“研究完成”状态源。只列论文和 GitHub 链接不能说明研究被使用。

硬预算、权限和兼容先筛；偏好再权衡。当前安装版本与文档承诺分别核，记录迁移和回退。小对照固定数据、用户身份、模型/工具版本、任务和预算；保留留出题、失败样本、作者介入和未观察项。剩余未知不再可能改变方向，或实验比继续搜索更划算时结束本轮研究；新事实只重开受影响决定。

## 本项目独立专业能力

长期项目从全局通用方法创建本项目独立能力与规则；已有项目包保留定制并原地迭代。输出 `projectCapabilityRequirements`，放在当前 productDesign 或当前非软件交接中；不得把同一需求复制成两个独立真源。

| 字段 | 应包含的专业内容 |
|---|---|
| projectId | 当前项目身份，不自动推断外部路径 |
| baseComponentId / baseComponentVersion | 全局专业基底及具体来源版本 |
| role / responsibilities / boundaries | 本项目负责的结果、相邻责任与排除范围 |
| domainEvidenceRefs / projectDelta | 领域事实依据；新增、收窄或替换的具体规则与理由 |
| reuseConditions / targetPath | 跨次任务适用条件；项目内目标；已有资产需原地迭代 |
| requiredInputs / toolRequirements | 具体数据、版本和工具能力，缺失时如何继续 |
| acceptance | 项目专业正例、反例和可观察通过条件 |

例如机电支持项目需型号/错误码、资料版本和部门权限，国风服装电商需产品事实、购买决策、尺寸与主题一致性。仅换角色名称没有形成领域能力。主题与偏好允许项目定制；关键约束的冲突交当前设计决定，不能静默覆盖已定用户要求。

这些字段供专业宿主生成/迭代真实 Agent、Skill 与规则。Node helper 只核给定合同和项目相对路径，不生成专业内容。实际文件、基底差异、版本/digest、加载和独立评审由调用方已有 projectCapabilityCreationArtifacts 等机制记录。需求已写、文件已生成、宿主已加载、真实效果已验证是不同事实。

## 回放反例

“开源所以无需成本和维护负责人”仍缺价值持续性；“卖高价所以必须复杂多 Agent”仍缺任务证据；“查过三篇新技术文章所以选型完成”仍缺决定消费；“全局专家更通用，无需项目包”遗漏长期项目专业差异。针对对应问题补证或修方法，不用更多标题、来源数量或生成文件数代替判断。
