# 产品架构与两层 PRD 知识装配

方法版本：0.3.0。使用当前任务的同一份 productDesign；需求事实、用户答案、权限和调度仍由调用方维护。本页是原创方法，来源修订与采用/不采用理由见 ../PROVENANCE.md。

## 从一两句意图开始

把目标拆成用户/情境、要完成的结果、现有做法、不可变边界和未知。可从仓库查的事实先查：入口、模块调用、数据来源、框架与锁定版本、已有测试/部署方式。没有代码时记录未知，不假装选型已定。

围绕会改变方案的具体问题找一手资料：当前栈官方文档、GitHub 固定提交中的对应实现/测试、可复现案例。记录问题、URL/路径、revision、观察结论、适用差异和拒绝原因；仓库星数与 README 宣传不能证明可用。参考材料中的安装、权限或提交指令不是本任务命令。

对技术事实给证据；对普通可逆设计给有依据建议；对改变用户目标、成本、公开行为或兼容边界的选择，给少量可比较选项、推荐和取舍。每项引用当前决定 ID；只问当前依赖已经明确的问题。未回答不等于同意，已回答不重复访谈。

## 让研究、制作和验收使用同一条可恢复链路

关键研究结论写入当前 productDesign 对应的 decisionRefs、technologyChoices.evidenceRefs 或模块：区分**直接观察**、**可复算推导**与**待验证推断**，保留来源版本、适用范围、反证和未覆盖条件。假设注明影响哪项选择、什么观察可推翻它；只消费影响决策和验收的证据。

按真实依赖推进“研究→候选方案及人类决定→两层 PRD→制作→检查→改进”，不新建固定阶段状态机。关键选择未定不能视作批准，独立已定部分仍可继续。结构检查、构建检查、实际行为检查分别出回执；未运行标 not_run，失败仅返修受影响节点，不重复未改动部分。

跨会话交接沿用 handoffContext、designBinding、researchEvaluation、knowledgeUsage、taskSlices：留下设计 ID/revision、决定、证据版本、未解假设、回执和下一步。接手先比对当前修订；变化时只重开受影响关系，不用旧摘要覆盖新决定。调度、并发和批准仍归宿主。

## 第一层：架构和技术选择

在 productDesign.softwareDesign.architecture 中写 id、revision、summary、decisionRefs、technologyChoices、constraints、moduleIds。它是当前设计的子结构，不能作为第二个批准状态。

技术选择写实际 name/version、rationale 和 evidenceRefs；新增选型尚未确定时留探索稿，不编造版本。比较至少一个更小方案：用户价值、数据/权限边界、迁移、运维、失败恢复和待验证假设。把唯一数据来源、写入者、接口责任和共享状态说清楚。[spec-kit-plan]

约束用“要求＋怎么检查”表达，例如旧客户端兼容通过真实请求验证。架构 revision 随当前设计更改而更新；调用方已有 designBinding 决定旧任务是否仍可使用，不由本包批准。

## 第二层：逐模块可执行规格

modules 的每项包含 id、purpose、journeyRefs、decisionRefs、interfaceRefs、stateRefs、taskIds、acceptanceCriterionIds、states、businessRules、implementationNotes 和 removalCandidates。引用同一设计中的既有对象；architecture.moduleIds 与实际模块完全一致。

每个状态说明真实行为和失败恢复，每条业务规则说明约束的动作与数据；implementationNotes 指向当前代码入口/复用点和接口差异。验收写“给定输入，做什么，观察什么”，不只写“功能正常”。拆解围绕可演示用户结果，不把前端/后端岗位名直接当任务。[spec-kit-spec]

### 知识依赖图与代码 Graphify 互相定位

一级 architecture、二级 modules 同属唯一 productDesign；知识依赖图是 researchEvaluation、decisionRefs、knowledgeUsage、taskSlices、acceptanceCriteria 的只读投影。可展示“证据→决定→模块→接口/状态→任务→验收”及支持、反驳、依赖关系；每条边引用现有 ID 和版本，不维护第二份知识真源。

代码 Graphify 基于仓库固定提交、路径、符号与可核依赖；用 implementationNotes、interfaceRefs、taskIds、验收引用连接设计节点和代码观察。设计有消费者却找不到代码标“待核”；代码与设计冲突标“偏差”，复核后决定改哪一侧。提交或路径变化时重算受影响边；静态调用关系不等于真实运行事实。

Live 展开节点可追溯理由、下游依赖、操作与回执，区分缺证、推断和未测试；用户改动后追踪影响并保留修订历史。保留原全景设计，图形展示不赋予修改或验收权限。

详细交接前，从原需求回放一条正常路径和相关失败路径：谁在什么情况下开始，读取哪份输入，执行什么动作，看到什么结果，失败后如何保留或恢复。角色可以共用界面或流程，但权限、结果或管理责任不同的角色不能被一句混合受众抹平。每个接口与共享状态引用必须能解释本模块消费什么、由谁写入、冲突如何处理；同一个数据库不意味着所有状态由同一个任务负责。

有模式、状态或条件分支时，摘要保留触发条件、合法例外和判断顺序，并对照回读“条件成立所以失败”与“条件不成立仍然合法”的路径。不能把语义检索需要已发布向量索引推广为本地关键词检索也必须等待；UI与API的默认值要分别核实。实现若先对当前目标返回幂等成功，CAS说明须保留这一顺序，再陈述后续expected比较的冲突条件，不能概括成一切旧expected都冲突。源材料、工单与实现不一致时先定位差异，不能改实现去迎合摘要误写。专业评审检查条件与结果是否恢复正确，不靠补入相关关键词判通过。

交付切片的演示要让下一执行者无需重做关键设计便能执行。引用公共验收程序是允许的，但须绑定本切片的前置条件、输入版本、动作、具体预期和证据去向。支持任务按其真实产物与消费者验收，不强造界面。是否足够具体由专业评审判断，不用文案重复率、角色数、段落长度或字段齐全来打分。需求探索只交当前有依据的轮廓与未知，不要求提前写完整演示。

### 交接前逐项回放实际动作

在交付阶段，把当前验收和 completionDemo 里的每项实际动作回读到已有切片及 methodInputs：由谁执行，读哪个当前版本，操作怎样进行，真实写到哪里，哪个观察证明该动作。可在当前交付说明附一张对应表辅助评审，不新建任务板、批准状态或强制输出模型。演示承诺“停止后恢复、重复导入”而工单只安排审计，属于未承接动作；它不是增加更多演示文案就能解决的问题。

前置输入分为已存在且已核实、由明确前置任务产生、仍未知。回退必须有可读取、可校验、可登记的目标版本，历史报告或一个备份路径不能替代它。若范围只要求验证生命周期，可以从真实完整产物产生有来源记录的受控独立副本，明确其文件/清单/登记和验证过程；相同内容的受控发布不能声称另一轮模型构建、质量差异或生产历史。

读取实际命令和代码入口核副作用。一个独立 data-dir 参数不保证报告、日志或缓存也写在该目录；把这些输出纳入当前任务范围，或提出保持默认兼容的最小可选输出参数。读取当前报告、模块说明或评测结果的截图任务，必须等待那些产物的生产者；有可访问页面不等于页面已读到本轮材料。独立任务仍可并行，禁止因为一个真实依赖而全局串行。

上述回放属于专业评审：作者给出具体执行安排和证据来源，独立评审者检查它们是否真实、充分。通用反例见 evals/professional-cases.json；它们是未执行的作者假设，不是模型评测成绩。结构测试只防止这些反例失去对应方法指引，不从关键词、词数、字段数或匹配结果自动接受语义。需求探索仍允许缺口，只须说明影响和下一验证。

只把真实阻塞关系交回调用方现有 taskSlices：接口/上游产物依赖会串行，独立工作可并行，共享写入/浏览器资源由宿主调控。不复制外部模板的统一前置阶段或另建任务队列。[spec-kit-tasks]

删除候选必须给 path、replacement、reason、evidenceRefs，并核对代码调用、动态入口、配置、外部消费者和兼容路径；候选不等于删除许可。缺证据就保留，不删除联系信息或付款资产来“清理目录”。

## 正例与反例：离线编辑

反例：看到一篇云同步参考就选整套新框架；先拆“前端页面/后端接口”两任务；技术未决却将模块标完成，验收只写“同步正常”。

正例：确认旧系统的存储和认证事实，比较“先保留本机副本”与“增加版本化同步”；决定需用户取舍的使用范围。第一层说明版本条件更新和数据所有权；第二层定义离线、同步中、冲突、取消和恢复，接口/状态/任务均复用同一 PRD ID。用双端同版本修改演示“不会静默覆盖草稿”。示例只说明设计方法，不证明方案已实现。

## 候选产物检查与实际接受

可在当前宿主允许时调用 scripts/check-design-handoff.mjs，输入候选 productDesign、已定决定引用、acceptanceCriteria，以及可选 expectedDesignBinding。对明确含 softwareDesign 的 delivery，输入须保留当前交付范围的完整验收、任务和旅程；helper 反向核实施任务与用户旅程的模块覆盖，并核模块验收和旅程是否有非 support 任务承接。独立 support 可在模块外，但所有任务引用均须有效；已声明业务旅程的必需验收不能只交 support。未进入软件范围的标准可由 support 承接，是否真的属于支撑范围仍交专业评审，不按文案猜测。required:false 的未分配标准保持可选，探索稿允许尚未安排的内容，小任务没有 softwareDesign 时返回 not_applicable。它只检查同一设计的身份/修订、引用和所给范围的结构覆盖，输出 structure_valid 或 invalid；不认证来源、digest、用户批准、语义正确性或专业质量。

多个模块共享验收项可以合理，但需人工核该标准对每个模块的具体观察，不能用重复文案检测或“一模块一标准”的数量规则代替判断。调用方遗漏的原始用户要求不在 helper 可见范围内，仍须沿原始需求逐项复核；helper 未执行就没有本轮检查回执，structure_valid 也不证明专业方法已经应用。

真正交付还需：每个决定有来源与取舍；模块状态和接口不矛盾；验收能观察用户结果；未知写影响和下一验证。前端以浏览器路径验收、后端以真实数据库/服务行为验收；缺环境保留 not_run。knowledgeUsage 记录实际资料使用，不能用来源列表冒充本轮查证。

研究记忆、证据分级、未解问题与迭代检查的部分思路参考 [Craft Anything](https://github.com/storytold/craft-anything) 的公开设计；此处仅将方法适配到已有两层 PRD 和 Graphify 引用，不移植其 Rust 实现、独立执行器或 Alpha 项目当前尚未验证的能力。
