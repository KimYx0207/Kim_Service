# 把审批任务设计成可恢复的完整交互

这是本包的原创合成工作样例，用于说明专业步骤、完整交付和拒收条件。它不是真实客户成果，也不是模型效果评测；实际任务替换输入与约束，按当前标准独立核验。

## 实务任务

合成任务：主管在手机和桌面审批采购申请。申请人可能在审批过程中修改数量；网络会中断。需交付状态设计、视觉约束和可验证原型说明，不预先绑定某个前端框架。

## 诊断顺序

先确认角色、决定所需材料和后果，再画页面。列出申请详情、预算/报价证据、审批记录及操作入口；将服务端版本、客户端编辑稿和当前提交状态分开。审批是用户判断，不应被默认勾选或动画自动推进。

## 状态与恢复样例

| 状态/事件 | 用户看到与能做的事 | 数据与焦点处理 |
| --- | --- | --- |
| 首次加载 | 有任务标题和加载提示；不显示假的零金额 | 加载结束不突然抢走用户焦点 |
| 无权限 | 说明不能查看的范围与可联系对象 | 不先渲染敏感报价再隐藏 |
| 可审批 | 金额、版本、依据与操作并列；拒绝需要理由时明确说明 | 按钮有可见名称，键盘顺序符合内容 |
| 发送中 | 显示正在提交，防重复；避免用无限转圈掩盖结果未知 | 保留决定和备注，不能提前显示“已批准” |
| 版本冲突 | 展示被改字段，要求基于新版本重新判断 | 原备注可恢复；旧批准不能套到新数量 |
| 超时未知 | 先查询操作结果，再允许安全重试 | 同一操作ID；不要直接再创建一次批准 |
| 成功 | 显示当前记录与提交时间，返回任务列表 | 回到合理位置；列表状态来自实际返回 |

## 视觉与可用性产物

visualSpec 要定义内容层级、间距/字体/颜色角色、关键断点、长标题、长金额、错误位置和减少动效的方案。阈值采用当前产品设计系统与可用性目标；不能为显得专业随意换字体或硬塞深色渐变。原型包含真实长度的示例数据和至少一次冲突恢复路径。

reviewEvidence 记录设备/视口、输入方式、操作序列、实际结果与未执行项。若使用模态框，检查初始焦点、Tab循环、关闭、背景不可操作和返回焦点；若任务需要并排查看报价，应比较页面内面板，不把模态当默认。

## 变体与拒收

- 批量审批要展示每项结果与部分失败，不能把请求成功视为全部通过。
- 大字/窄屏下关键信息与操作不能消失；横向滚动表格须有可理解的导航提示。
- 提供截图只证明某一画面；无交互证据不能宣称键盘或读屏已验收。
- 错误清空备注、冲突后默认沿用旧决定、操作失去焦点、缺少权限态，均属于交付缺陷。

## 使用与来源边界

方法依据沿用本包 PROVENANCE.md 的已登记专业资料。上面的数字、场景和交付表是原创合成示例；来源列表不证明当前任务已联网取证。先读取 professional-method.md 确认适用范围，再将本例迁移到当前事实；无法验证的结论交明确缺口，不填写成功回执。
