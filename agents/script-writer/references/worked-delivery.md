# 将一个观点做成可读、可拍、可核的脚本

这是本包的原创合成工作样例，用于说明专业步骤、完整交付和拒收条件。它不是真实客户成果，也不是模型效果评测；实际任务替换输入与约束，按当前标准独立核验。

## 合成任务

写约60秒口播，解释为什么“表格去重”先要确定业务键。素材只有一张合成订单表和一条反例：同一客户两次购买不是重复订单。目标是让观众知道下一步该核哪些字段，不承诺软件自动完成所有业务。

## 完整制作结构

| 时间预算 | 内容责任 | 画面/证据 |
| --- | --- | --- |
| 0–5秒 | 给具体处境：删重后订单金额对不上 | 去重前后差异，不伪装真实客户案例 |
| 5–15秒 | 指出冲突：同名客户不等于同一订单 | 两笔合法购买对照 |
| 15–40秒 | 演示核订单ID、渠道与状态，再查重复键 | 标出字段与保留记录理由 |
| 40–55秒 | 给安全动作：保留原表、对账后再使用结果 | 记录数/关键合计与异常列表 |
| 55–60秒 | 收束到一个行动 | 先写清“什么算一笔订单” |

## 可进入读测的完整口播草稿

“表里两个客户名字一样，就删掉一条？先停一下。你删掉的，可能是一笔真的订单。

看这张演示表：小王上午买了一次，下午又买了一次，两个订单号不一样。这不是重复。另一种情况，同一个订单号被导入了两次，才需要继续核对。

先把订单ID、渠道和状态放在一起看：这个编号在哪个系统里才唯一？两行是同一次购买，还是不同状态的更新？规则确定后，再决定保留哪条，别让软件替你猜。

处理前留一份原表，处理后对数量、金额，把解释不清的记录单独列出来。别只看行数变少了，就说处理成功。

你现在可以做的第一步，是在表格旁写一句：我的业务里，什么才算同一笔订单？”

屏幕文字依次为“同名 ≠ 同单”“核业务键与状态”“保留原表、核数量和金额”。只使用合成表，画面明确标注“演示数据”。上述是完整草稿，时间表是编辑预算；需按实际画面、停顿和读速读测，调整后才报告实测时长，不能据字数估计就宣布正好60秒。

## 专业审查

oneLiner只能承载一个主判断；hooks给不同真实开场，不能为冲击力编惨痛损失。content明确口播、画面、屏幕文字与音效的对应，不能写无法拍摄的抽象动作。claimsCheck把事实、个人判断和合成示范分开，外部事实核来源与日期。读一遍检查主谓宾、指代和停顿，再按实测耗时删重复句。

## 拒收

开场承诺与正文无关、反例不能支撑观点、把合成表说成真实收入事故、只给提纲而用户要完整稿、未读测就称时长达标，均需修改。推广内容中的价格/权益/限制需核当前brief与真实条件。

## 使用与来源边界

方法依据沿用本包 PROVENANCE.md 的已登记专业资料。上面的数字、场景和交付表是原创合成示例；来源列表不证明当前任务已联网取证。先读取 professional-method.md 确认适用范围，再将本例迁移到当前事实；无法验证的结论交明确缺口，不填写成功回执。
