# 游戏经济与成长系统设计师：合成交付演练

所有数值、条款、设备、账户和业务对象均为合成教学材料；预期判断尚未经过真实行业任务评测。

## 输入

```json
{
  "economy": {
    "currency": "金币",
    "opening": 10000,
    "minted": 3000,
    "burned": 2500,
    "playerTransfers": 1200,
    "duplicateRewardEvent": {
      "id": "E1",
      "amount": 200
    }
  },
  "cohorts": {
    "new": {
      "dailyEarn": 100,
      "requiredSpend": 120
    },
    "mature": {
      "dailyEarn": 500,
      "requiredSpend": 200
    }
  },
  "constraints": "检查守恒与成长公平；未连接生产钱包"
}
```

## 分析与可复核结果

合成玩家群体，单币种金币：期初总存量10000，一天任务奖励产出3000，升级销毁2500，玩家间转账1200。系统期末应为10500，转账不减少总量。若活动事件E1奖励200因回调重试记两次，会多增200；应保留唯一业务事件与参数，第二次返回已有结果。
新手人均每日赚100、必要升级花120，成熟玩家赚500花200，整体存量增长不能证明新手体验顺畅。应分别检查阶段成本与参与时间，不能直接全局涨价。

## 当前交付字段

- `economyMap`：金币系统期初10000、系统产出3000、销毁2500；玩家内转账1200只变分布，不改总量；E1奖励200需与产出明细核是否重复计入。
- `balanceSimulation`：按给定产出/销毁且无额外重复记账，期末10500。新手100−120=−20/日，成熟玩家500−200=+300/日；群体人数未给，不能推总体均值。
- `transactionControls`：E1以业务事件ID、玩家、币种、金额和规则版本绑定重复请求；同参数返回原结果、冲突参数交核查。没有生产流水或行为测试，不能称实际幂等已通过。
- `tuningPlan`：优先查E1重复与新手必要消耗缺口，分别评估奖励/成本参数；不全局涨价。保留原配置、阶段达成时间和净产币监测，阈值及上线动作由实际目标和权限确定。
- `facts`：本例所有对象和数值为合成，来源是本页input对应字段；未提供的真实文档、观察日或外部事实均不补造。各已给单位、日期和条款版本按原字段保留。
- `limitations`：仅完成所示条件推导与文本分析；未连接实际业务系统、未验证真实来源，未执行外部变更。缺口及其影响已经分布到各领域输出。
- `handoff`：本页作为合成交付示范；实际任务按delivery-template和method.json交同名字段、原材料位置与逐项检查证据。将上述待核材料交当前调用方继续，不创建新的授权或业务状态。

以上覆盖当前合同全部必填字段；它是合成输入的完整交付演练，不是实际业务验收。

## 看起来完整但应拒收

```json
{
  "balanceSimulation": "总量=10000+3000-2500-1200=9300；所有玩家都很富，统一涨价。"
}
```

把系统内转账算销毁，且用总体存量掩盖新手资源缺口。
