# 从通用方法到项目体验规则

本方法适用于收到项目体验上下文的专业任务。四层规则属于调用方当前 `productDesign.projectExperience`，经 `designContext.projectExperience` 投影给当前任务；`designBinding` 仍是唯一设计身份。本文、helper 和合成例随本角色独立复制，不依赖仓库外的全局文件。共同方法的维护源为 interaction-designer 同名文件，其他角色随包保留相同副本；修改后核对四包并执行各包测试。

## 先形成这个项目自己的专业规则

每个项目均保留独立的专业规则与适用依据，通用方法提供基础。先读取调用方已经建立的项目能力及规则；缺少时交回具体差异、材料和建议，由调用方沿现有项目能力创建与 ownership 登记流程保存。需要改变专业方法时派生当前角色的方法包；只需项目参数时也要保留本项目的领域任务、品牌、页面规则和来源，不能只写一个全局方法名字。普通任务继续使用已存在的项目规则，不反复创建副本。

| 层 | 要写的事实和判断 | 会改变的产物 |
| --- | --- | --- |
| base 通用专业基础 | 任务可理解、状态可发现、输入可恢复、键盘/焦点/阅读顺序、真实内容可读 | 各页面和组件共用的可操作底线 |
| domain 行业任务 | 谁在什么情况下判断什么；领域对象、专有字段、失败后果及来源 | 导航、比较项、主次信息、业务状态和验收任务 |
| brand 项目品牌 | 当前品牌依据、语义 token、图片/字体/语言风格、目标设备 | 组件样式与内容表达；不替代行业任务设计 |
| task 当次页面与流程 | 本切片的入口、页面状态、决策信息、动作、退出、失败恢复 | 当前模块规格、组件状态、实际实现和验证路径 |

每层记录资料 `ref` 和适用 `version`，已有 digest 一并保留；相同关切和目标的变更显式写 `overrides`，保留来源链。通用必需项可细化；删掉关键状态、输入保留或可达路径属于待解决冲突。主题 token 可按项目覆盖，但还需核实际组合的对比度、密度与长内容。原生宿主同名 Agent 的替换规则，与这里的专业规则组合是两件事；项目独立包不会因同名自动继承或自动升级。

## 按用户当前决定分配信息

1. 同一事实明确主展示位置。摘要、精确表格、最终确认可为不同任务重复，但要说清各自用途；不按文字重复率自动删内容。
2. 主显用户当前决定必需的信息：当前状态、主要动作、错误及恢复、价格/安装条件/答案依据等适用项目项。简洁是减少寻找和误解，不能仅以卡片少、文字短、留白多判断。
3. 把长背景、低频设置、详细日志等放在可发现的展开入口。若用户需阅读全部内容，直接展示并用标题组织；错误或购买关键约束不藏在折叠里。折叠名称说明其中内容，键盘和展开状态可被感知。[carbon-disclosure]
4. 图表达关系、流程、空间和趋势；精确规格、价格和逐项核对保留可读数据。图表有明确消息、单位和必要说明，关键数据不能只能悬停查看。文字摘要、可访问数据与图各承担作用。[uswds-visualization]
5. 设备、语言、输入方式决定布局密度和交互目标；不强制所有页面同一种大小或卡片结构。键盘、焦点、对比、缩放与真实错误恢复仍须实际检查，自动扫描不替代任务观察。[wcag22]

## 四个差异例与反例

以下为作者设计假设，不是用户观察。机器可运行的候选模型见 `examples/project-experience/cases.json`。

| 项目 | 行业任务与应主显的信息 | 适合延后或展开 | 应拒绝的候选 |
| --- | --- | --- | --- |
| 机电维护 | 异常设备、严重度/影响、责任人、工单；保存失败保留处置记录 | 完整维修历史、诊断日志 | 用购物卡片代替异常分级，把故障状态折叠起来 |
| 日常国风服装 | 款式、面料、版型、尺码与库存、价格；失败保留所选规格 | 品牌故事、长工艺介绍 | 只换红金配色，把尺寸适配和缺货藏入说明 |
| 家电选购 | 精确尺寸、安装条件、能力与总费用的比较 | 详细技术原理、完整说明书 | 只有漂亮雷达图，找不到准确尺寸和安装限制 |
| 企业知识库 | 答复、适用边界、来源版本及可打开的证据；无依据时提供继续路径 | 长摘录、检索细节、维护日志 | 用“生成成功”掩盖无依据，把来源和限制都折叠 |

Shopify 的细分主题方法采用“购买决定、品牌表达、目标人群和库存结构共同影响组件”的判断；其商家后台和商店样式不直接套用到机电或知识库。[shopify-theme-segments]

## 各专业角色怎样消费

- 用户研究：把领域任务转成会改变选择的问题及不提示答案的任务卡。将材料事实、设计假设、参与者观察分开；记录如何支持或反驳本项目规则。没有参与者材料时交研究计划与待验证项，不填访谈人数或完成率。
- 交互设计：为关键决定写可见信息、展开信息、表现形式及理由，落到当前页面状态；实际内容与失败路径先于润色。效果方向有实质取舍时，比较任务成本和误解风险。
- 设计系统：将有效品牌规则落实到语义 token 和组件 API，用项目真实内容验证；机电工单、尺码选择、安装比较、知识来源各用对应状态试用，不能只有同一组件墙换色。
- 前端实现：从同一版本的项目规则与交互规格实现真实入口。浏览器观察回到具体任务，检查展开、长内容、键盘、失败恢复和接口结果；设计模型声明不替代 DOM 或实际操作。

## 交付和验证

交付原有角色成果，并补 `experienceApplication`：哪条有效规则改变了哪项产物、具体怎么改变、证据位置或尚未执行的原因。研究阶段可只交决定与验证任务；设计/实现阶段还应将需要验证的页面状态写入 `surfaceModels`。规则 ID 回显本身不构成应用。

可在宿主具备本地 Node 能力时使用 `scripts/project-experience.mjs`，接口见 [project-experience-api.md](project-experience-api.md)。它实际解析四层规则，保留来源，生成按任务的有效上下文，并查候选模型是否藏了必需信息、缺状态、缺精确值、丢恢复输入或与当前版本不符。它返回 `review_required`，从不判定 UX、用户研究或实际宿主调用已经通过。浏览器与真实用户证据由现有验收过程检查。

验收给实际环境、输入/动作、预期、观察、产物版本和限制。用户独立完成与提示后完成分开，时间/成功率使用真实分母；专业审查、合成案例和真实用户结果分别记录。发现问题时定位到通用方法、项目差异、调用方漏装资料还是实现，修对应处并重验受影响路径。
